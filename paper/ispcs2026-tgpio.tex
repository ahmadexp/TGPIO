\begin{abstract}
Distributed applications use synchronized clocks to coordinate software processes across multiple systems. A subset of these applications, for measurement and control, often needs to interact with the physical world. Time-Aware GPIO (TGPIO) enables this interaction using the software-visible synchronized clock to timestamp externally driven input signal events and generate an externally visible output signal. This paper presents a Linux driver for the TGPIO hardware that exposes an API conforming to the standard Linux PTP hardware clock (PHC) interface, enabling the use of standard tools such as \texttt{ts2phc} and \texttt{phc2sys} without modification. The driver provides greater flexibility than the TGPIO PPS drivers available in upstream Linux. To evaluate time synchronization accuracy, we compare the PPS output from the TGPIO to that of the atomic-clock-referenced OCP TimeCard. The disciplined TGPIO 1~PPS output holds a \ns{+9} mean offset (\ns{64} standard deviation), making its time accuracy comparable to the TimeCard's own PPS.

Measured against the atomic-clock-referenced PPS of an OCP TimeCard, the disciplined 1~PPS output holds a \ns{+9} mean offset (\ns{64} standard deviation), comparable to the TimeCard's own PPS.

\section{Introduction}\label{sec:introduction}

Real-time systems often need physical I/O that bridges software events to hardware signals on a shared timebase. Typical functions include timestamping a pulse-per-second (PPS) input, measuring an externally generated instrument trigger, and generating a scheduled output transition to actuate a state change in a device under test. Linux already handles this class of application I/O through the PTP hardware clock (PHC) abstraction, covering both timestamping external input signals and generating periodic output signals \cite{linux-ptp-docs}.

Consider a system that must derive time from a GPS receiver without a PTP-capable NIC, FPGA, or dedicated timing card. TGPIO hardware captures a timestamp corresponding to the receiver's PPS output edge, exposing the timestamp as a PHC external timestamp (EXTTS) event. Standard Linux PTP tools can read the TGPIO PHC's relation to the system clock and discipline the system clock to track GPS time. This minimal time synchronization path from an external time reference to Linux timekeeping enables many of the same applications that use Time-Sensitive Networking (TSN) for clock synchronization \cite{ieee8021as}.

%% There is a gap when employing certain platforms. The timed I/O resources are physically present and functional, but firmware has not enumerated them, so they are not found by the normal platform-driver discovery path. The result is that applications do not have a standardized way to reach hardware useful for time synchronization and measurement.

This paper describes an out-of-tree Linux driver that exposes additional capabilities beyond the upstream driver for the Intel Time-Aware GPIO (TGPIO) device. Most Intel platforms have two TGPIO pins, each controlled by a dedicated register block. The driver maps the physical pin and its register block to a PHC channel and pin accessible from software. A PHC pin can be configured as an EXTTS input, a periodic output (PEROUT) generator, or disabled. The design leans on the Linux PHC interface instead of a bespoke user ABI, enabling use of existing unmodified tools like \texttt{testptp}. A companion Python library, \PyLib, wraps the PHC character-device interface, facilitating scripted experiments \cite{pyptm-repo}.

The TGPIO hardware timestamps events using the Always Running Timer (ART). By default, the driver reports timestamps in terms of ART. This simplified usage was useful for bring-up and debugging. However, disciplining the system clock requires timestamps in terms of the system clock rather than ART. One of the major implementation challenges was translating between ART and system time to enable this.

This work makes five contributions. First, a PTP-clock abstraction that enumerates, initializes, and configures the hardware, with per-pin selection of functionality (\ie EXTTS, PEROUT, or disabled). Second, a timestamp path that supports raw ART timestamps, conversion of ART timestamps to \ClRT, and a default ART-backed adjustable PHC mode for use with tools such as \texttt{ts2phc}. Third, a test harness used for initial bring-up and ongoing driver development. Fourth, a one-shot external calibration that measures and corrects for hardware pipeline delays (\eg buffering), holding a disciplined 1~PPS output within \ns{100} of an atomic reference. Finally, a Windows KMDF port of the same blocks that reuses those hardware findings unchanged, separating the common TGPIO driver design from the operating-system specifics.

\section{Background}\label{sec:background}

\subsection{Linux PTP Hardware Clocks}

Linux exposes peripheral device clocks through the PHC subsystem. Usually the device clock is the NIC timestamp clock used for the PTP protocol. The PHC subsystem provides a POSIX clock interface to get and set the time and a character device with ioctl commands to find the relation of the timestamp clock to the system clock, and control I/O pins that are driven by the timestamp clock. On the kernel interfacing side of the PHC subsystem the driver registers a \texttt{struct ptp\_clock\_info} that provides I/O pin information and several callbacks the PHC subsystem uses to configure and read the hardware state. The PHC subsystem uses \texttt{gettime64()} and  \texttt{settime64()} callbacks to get and set the device clock time. The \texttt{enable()} callback configures the device's I/O pins and is exposed to user code using ioctl commands. The key pin functions are \texttt{PTP\_PF\_EXTTS}, which emits timestamped edge events, and \texttt{PTP\_PF\_PEROUT}, which requests a periodic output \cite{linux-ptp-docs,linux-ptp-header}. We repurpose the PHC interface to control the TGPIO device. This avoids adding a new device class to the kernel and leverages existing tools to interface with the TGPIO device.

\subsection{ART, TSC, and Cross Timestamps}

Modern Intel platforms use the Always Running Timer as the basis of hardware timekeeping on the platform. The Time Stamp Counter (TSC) is used for CPU timekeeping. TSC is locked to the ART by a fixed ratio that can be discovered by software using CPUID leaf \texttt{0x15} which also reports the ART clock frequency. The CPUs that support  \texttt{0x15} are listed in the \cite{intel-sdm}. Linux timekeeping, for example CLOCK\_REALTIME, on Intel platforms in based on TSC. Given the fixed ratio between ART and TSC, ART can also be related to CLOCK\_REALTIME \cite{linux-timekeeping-docs,linux-crosststamp-rfc}. The TGPIO device is driven by ART extending the Linux system clock to a physical pin where CLOCK\_REALTIME can be used to sample or generate a signal.

\subsection{Firmware Enumeration Gap}\label{sec:device-enumeration}

Despite extensive public discussion proposing support for the TGPIO (sometimes called ``timed I/O'') support in Linux \cite{linux-pps-gen-tio,lkml-tgpio-pmc,lkml-tgpio-io}, the platform studied does not expose the TGPIO device addresses using ACPI. This is true for most platforms as BIOS developers have declined to include support for TGPIO. To remedy this, the driver takes the MMIO base addresses used by the TGPIO device as a module parameter. These addresses are platform dependent, requiring an additional step by the user to get the device base address from the hardware documentation.

\subsection{PTP Pin Model}

At load time, the driver maps all enabled blocks and registers a single PHC device clock, with each TGPIO pin and corresponding register block represented by a PTP pin descriptor named by its physical index and mode. Pin verification accepts external timestamp requests only on input-mode blocks and periodic-output requests only on output-mode blocks. Channel mapping follows the PTP pin assignment model (\texttt{testptp -L}); absent an explicit assignment, the driver falls back to a direct channel-to-block mapping.

\subsection{Userspace Control}

The control interface is the standard PTP character device rather than a private ABI. \texttt{testptp} handles pin assignment, external timestamp enablement for input\footnote{Due to a PTP core change in v6.16, older kernel versions may behave unexpectedly with respect to input event flags; a driver must advertise \texttt{supported\_extts\_flags} for the strict \texttt{PTP\_EXTTS\_REQUEST2} ioctl to succeed.} and periodic output. PyLib exposes the same operations using a Python wrapper module.

\subsection{External Timestamp Input}

For input mode, enabling a PTP external timestamp request configures the block for input, applies the edge selection (rising, falling, toggle / both edges), and starts a polling worker thread that reads the capture timestamp and event counter. The register sequence matters: ART is a 64-bit counter and is accessed using two 32-bit reads (bit 0:31 and  32:63). On current Intel platforms, the lower 32-bits roll over every 1.9 minutes for client platforms or 2.9 minutes for server platforms. On detection of an edge, the hardware latches the lower 32-bits of ART. No other events can be timestamped until software reads the capture register. The upper 64 bits are not latched. The software must account for the rollover in the lower 32-bits when synthesizing the 64-bit ART value.

Software detects an event capture by polling the latched ART value and/or the event count. When the driver detects an event, it emits an external timestamp event through the PHC event path using the timestamp type selected by the timestamp mode.

\subsection{Periodic Output}

For output mode, a PTP periodic-output request supplies a start time and period in the PTP clock's time domain. The driver rejects unsupported perout flags, validates the period, computes a half-period, and requires that Linux timekeeping expose an ART base clock. It then converts the requested start time into an ART compare value and the requested half-period into an ART interval value before programming the hardware.

Steady-state output uses the TGPIO hardware periodic feature: the comparator holds the first active edge, the interval register holds the half-period in ART cycles, and the periodic-mode bit lets hardware generate subsequent toggles without per-edge software work. The output level flop is an internal register whose value cannot be read.  It holds the last generated level and survives enable/disable cycles. The driver replicates the internal register value in software: it assumes the power-on low state at load, folds every generated toggle into the register clone via the event count (EC) register.  The driver waits for the low before stopping and unloading so the assumption survives reloads. A guard pushes a late first compare forward by whole periods (a compare already in the past fires immediately and would invert the waveform), and a debugfs control flips the register clone if interference ever falsifies it, shifting a running waveform by half a period without a glitch. The same engine serves asymmetric duty cycles whose halves are both at least 50~ms by alternating the interval register between on-time and off-time counts (a 25\% duty request measured 249.998~ms/749.995~ms) and provides hardware-timed one-shot pulses; an hrtimer path remains for narrower pulses. One negative result is worth recording: with a 50\% duty output, edge timestamps alone cannot distinguish rising from falling edges, so polarity is unobservable from an external reference, becoming observable (and self-correcting) only in a loopback configuration where an input captures the output's own rising edges.

Quantization is reported by the driver and not abstracted. Converting a request into an integral ART value rounds both the half-period and the first edge, and every arming of a cycle logs the residuals for the rising and falling edges. The debugfs status file exposes the same quantities continuously, with the live phase error of the pending edge and the tracked output level.

The driver supports three PTP clock modes; internally, the TGPIO registers always use ART-domain counter values for both capture and compare. The default mode exposes an ART-backed adjustable PHC with \texttt{settime64()}, \texttt{adjtime()}, and \texttt{adjfine()} support, so a GPS PPS signal connected directly to a TGPIO input can become the external reference for tools such as \texttt{ts2phc}, after which other Linux time tools can make the disciplined time available to the system. An \texttt{art} mode reuses the same anchor-plus-rate clock model but rejects adjustment requests, providing an undisciplined hardware-paced timebase; calibrating its rate against \texttt{CLOCK\_MONOTONIC\_RAW} can only recover the nominal ratio (that clock is mathematically related to the ART or crystal frequency, so the crystal's ppm-scale error remains), while an alternative realtime calibration tracks the kernel timekeeper's rate with a sliding-window estimator and a runtime trim accepts an operator calibration if available from an external instrument.

An explicit realtime mode ties \texttt{gettime64()} to \texttt{CLOCK\_REALTIME} and passes through the PTP adjustment operations to the system clock. Because that clock is also steered behind the driver's back (\texttt{chrony}, \texttt{adjtimex}), realtime-mode outputs are re-synchronized to the realtime grid once per second using the same glitch-free nudge machinery as PHC mode. A reference pulse captured by a TGPIO input can then discipline the operating-system clock directly from hardware timestamps; validated with a \texttt{chrony} PHC-refclock configuration, the system clock locked to the atomic PPS with a $-218$~ns offset and 11~ns per-sample standard deviation. This gives the OS a local disciplined timebase for host-side timestamping and scheduling that is aligned with the external clock source; time-triggered process scheduling or network transmission still depends on the NIC hardware and other software stacks.

For input events in realtime mode, the driver constructs a device cross-timestamp context from the captured ART cycle count and the Linux ART clocksource identifier, calls the kernel cross-timestamp interface, and uses the returned realtime value as the event timestamp; in PHC mode, captured cycles are converted into the adjusted PHC domain by applying the current offset and frequency scale. The raw ART mode claims no realtime epoch alignment.
Realtime mode converts through Linux timekeeping's realtime-to-ART relationship; PHC mode uses the driver's stable ART base rate plus the adjusted TSC offset and frequency scale; the periodic interval register uses the same conversion.

A running hardware output must also follow PHC discipline. The nominal CPUID crystal frequency differs from atomic time by tens of ppm on the tested platform. A PHC step re-arms the output with the first edge advanced along the originally requested period grid, so a step never shifts the waveform phase. A frequency adjustment rewrites the periodic interval register in flight (such writes latch cleanly for subsequent periods), and residual phase errors greater than the ART period, measured against the pending edge read live from the comparator, are corrected by rewriting the comparator, which moves only the pending edge and produces no glitch. Finally, a runtime-writable calibration offset shifts every programmed edge by a constant, compensating for any fixed offsets in the system.

\section{Bring-Up Lessons}\label{sec:bring-up-lessons}

Several implementation details emerged only during bring-up. First, the input default was changed to rising edge: both-edge capture doubles the apparent event rate and rarely matches PPS or trigger workflows.

Second, the modes need different dependency checks. Raw ART conversion and hardware periodic intervals require an ART frequency value (supplied or CPUID-detected) while realtime conversion relies on Linux timekeeping's ART clock relationship; the driver reports the CPUID values for diagnostics.

Third, the output semantics were settled only by direct register experiments observed with a logic analyzer, and several contradicted the initial mental model. Because the captures were scripted, each wrong hypothesis was falsifiable within minutes, and this loop of poke, capture, and decode was the most productive bring-up tool. One caveat surfaced only here. A comparator rewrite can record a phantom event that flips the register parity, so the driver pauses the periodic-mode bit around such rewrites while output enable holds the line level.

\section{Evaluation}\label{sec:evaluation}

The tested platform is an ASUS ProArt Z890-CREATOR WIFI motherboard (BIOS 3202) running Ubuntu 26.04 LTS with Linux \texttt{7.0.0-27-generic}, using the default addresses and two-block setup. The reference is an OCP TimeCard whose PHC (\texttt{ptp\_ocp}) is fed by its onboard atomic clock. A Saleae Logic Pro 16 samples four channels at 100~MS/s (10~ns resolution), observing the atomic 1~PPS, the TimeCard PPS, and both TGPIO outputs; the analyzer's crystal error cancels because all results are channel-to-channel differences against the atomic PPS. \texttt{phc2sys} disciplines the TGPIO PHC from the TimeCard PHC at eight updates per second.

Table~\ref{tab:eval} summarizes the output results. Once \texttt{phc2sys} locks the TGPIO PHC to the TimeCard, the interval-refresh path removes the rate error entirely: over two-minute captures the mean period matches the atomic reference at the instrument's resolution, with zero waveform restarts and driver-reported phase error below 100~ns. The residual $+2.38$~$\mu$s offset before calibration is constant (drift below 1~ns/s) and dominated by asymmetry in the PHC-to-PHC comparison: reading the TimeCard PHC across PCIe costs several microseconds round trip while the TGPIO read is a low-latency conversion using the kernel timekeeping logic, and \texttt{phc2sys} assumes the PCIe clock is sampled at the transaction midpoint. Writing the measured constant offset into a calibration parameter moves the output to $+9 \pm 64$~ns, statistically comparable to the TimeCard's own PPS on the same instrument ($-10 \pm 54$~ns); the remaining spread is consistent with the 26~ns ART quantization step plus servo wander. Reaching this floor also required disabling CPU power management by writing zero to \texttt{/dev/cpu\_dma\_latency}. The performance cpufreq governor disables hardware CPU throttling to stabilize the PCIe read latency, and the constant must be recalibrated if that configuration changes. Enabling PCIe PTM eliminates these software and PCIe read-latency asymmetries entirely.

Polarity determinism was validated separately: across five module reloads, deliberate 300~ms PHC steps, and \texttt{phc2sys} restarts, both outputs produced a rising edge at the requested target time each iteration, and a falsified register clone was corrected through the debugfs control while running, snapping the inverted waveform onto the grid without glitching.

The hardware-domain loop was then closed: the reference PPS was wired into a TGPIO input and \texttt{ts2phc} disciplined the PHC from that block's own ART-domain timestamps, with the second block generating the output. Capture and generation share the ART timebase, so the PCIe comparison drops out entirely: the uncalibrated offset collapses from $2.4$~$\mu$s to about $+50$~ns (roughly two ART cycles of pipeline difference), with no latency pinning required. Alignment measured $-52 \pm 122$~ns against a reference whose own wire-to-wire noise floor was 60--80~ns. Both discipline paths therefore land within about $\pm 100$~ns of the atomic reference, the input-capture path being preferable because its systematic error needs no external calibration. This configuration is the complete GPS use case with the atomic PPS standing in for a receiver.

The alternate clock modes were characterized in the same setup (Fig.~\ref{fig:ptmrun}, right). ART mode with the default same-crystal calibration drifts at the crystal error ($-41$~$\mu$s/s measured); with realtime calibration the sliding-window estimator holds the residual rate to tens of ppb, and the operator trim removes the remainder after one instrument measurement. Finally, enabling PCIe Precision Time Measurement on the master TimeCard (hardware cross-timestamps through \texttt{PTP\_SYS\_OFFSET\_PRECISE}) removed the software-bracketed read asymmetry from the phc2sys comparison entirely: both legs then rest on hardware-paired timestamps, the delay calibration becomes unnecessary, and a 22-minute common-view run with zero calibration showed smoothed output phase wander of about 10~ns RMS against the shared atomic reference with drift below $10^{-11}$ (Fig.~\ref{fig:ptmrun}). \section{A Windows Counterpart}\label{sec:windows}

The register-level semantics of Section~\ref{sec:bring-up-lessons} are properties of the device and not of Linux, so they should transfer to any operating system able to map the same MMIO. We brought the same two blocks up under Windows as a KMDF driver, which both validates the claim and serves users who do not run Linux. The driver is a root-enumerated software device, the direct analogue of the Linux module's static addressing: it claims no PnP resources and maps the physical addresses itself through \texttt{MmMapIoSpaceEx}, with addresses, span, block count, and ART frequency in the service registry key, seeded by the INF with the defaults of Table~\ref{tab:params}.

Since Windows has no PHC abstraction, the control plane of the port diverges from the Linux implementation, as there is no clock device for \texttt{ts2phc} or \texttt{phc2sys} to bind to and no pin-function model. Instead, the driver exposes a small set of buffered IOCTLs over one sequential queue with capture delivery pull-only. Lacking a correlated-counter interface, the driver brackets a \texttt{KeQuerySystemTimePrecise()} read between two \texttt{RDTSC} samples and converts through the CPUID leaf \texttt{0x15} ratio, but that rate is nominal and never refined. The Windows output free-runs at the crystal's ppm error, which is the same limitation as the Linux ART mode.

However, the output engine did carry over intact. It reuses the same toggle-mode periodic output, whole-period late-arm guard, software register clone of the level flop, and paused comparator rewrite for glitch-free inversion. The code was written straight from the findings of Section~\ref{sec:bring-up-lessons} and worked without further hardware discovery, the strongest available evidence that those findings describe the device rather than the driver. The driver produces a UTC-aligned 1~Hz signal, but we have not repeated the measurement campaign, so every number in this paper comes from Linux.

\section{Limitations and Future Work}\label{sec:limitations-future-work}

The current implementation is intentionally platform-specific: it requires known MMIO addresses and should only be loaded where those have been confirmed. A production-quality upstream driver would need robust platform discovery and device configuration checks. The external timestamp path is polling-based, which keeps the driver compact but creates a system load / event-loss tradeoff controlled by \texttt{poll\_ms}; an interrupt-backed path would be preferable for high-rate streams. The default PHC mode adjusts a software clock model layered on ART rather than disciplining the underlying oscillator itself, unlike a NIC PHC that contains an independent hardware clock.

Output polarity ultimately rests on one bit of external truth: the level flop cannot be read, so anything toggling the pin outside the driver requires a one-shot external observation to correct through the debugfs flip control. Tools holding the PTP character device open must also be restarted after a module reload, because the clock device is recreated.

Future work includes the remaining timestamp-mode comparisons, repeating the measurement campaign on the Windows port, and evaluating whether a subset of the design is suitable for upstream Linux review.

\section{Conclusion}\label{sec:conclusion}

This work shows that firmware-undeclared timed I/O hardware can be made useful through the standard Linux PTP interface: presenting each mapped TGPIO block as a PTP pin lets existing tools control hardware that would otherwise be unreachable, and a direct TGPIO input provides a compact path from an external time reference into host timekeeping.

The decisive engineering issues are clock-domain correctness and deterministic output behavior, addressed with explicit timestamp modes, cross-timestamp conversion, realtime-to-ART scheduling, and a software register clone of the level flop. With in-flight interval refresh, live comparator phase nudges, and a one-shot delay calibration, a disciplined TGPIO output holds an external atomic PPS reference within 100~ns, comparable to a dedicated timing card's own output. The Windows port reinforces the division of labor: the hardware semantics carried over unchanged, while the clock integration had to be rebuilt around what that operating system exposes.
